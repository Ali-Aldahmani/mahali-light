# EDARA POS — AI/ML Feasibility & Data Readiness Audit

**Audit date:** 2026-10-24  
**Repository revision inspected:** `f6bb3c0` (`f6bb3c0c980fbb64b2605c0d33b0cce1adbbfb5e`) plus the pre-existing working-tree state noted below.  
**Scope:** Read-only source, migration, configuration, and test inspection. No database connection, production records, writes, endpoint execution, dependency installation, model download, or application changes were used for this audit.  
**Evidence limitation:** SQL files are migration definitions, not proof those migrations ran. Historical row counts, data completeness, applied schema version, retention, and model training sufficiency are **NOT VERIFIED**.

## 1. Executive Summary

The POS has a conventional, viable foundation for advisory analytics: PostgreSQL 16 is defined in Docker Compose; the primary application is Node.js/Express with `pg`; the web UI is Next.js/TypeScript; sales lines retain sold quantity, transaction price, discount, and cost-at-sale; stock movements preserve timestamped quantity deltas; purchase orders track ordered and received quantities; and returns, payments, expenses, attendance, cash, and bank records have dedicated schemas. Authenticated routes use per-permission checks. A monthly deterministic reorder/annual-plan calculation already exists.

The repository does **not** establish readiness for a comprehensive ML platform. The existing forecast is a simple rules-and-averages feature, not a trained model. Sales history is reduced to monthly aggregates for the current forecast path. There is no branch, warehouse, or tenant/company key in the reviewed business schemas; no normalized receipt-event or inventory-lot/expiry model; no explicit price/promotion history; no visitor counter or staff schedule; and no ML model registry, training pipeline, evaluation store, queue, or prediction lifecycle. The optional FastAPI container is a small read-only API slice, not an inference/training service; the declared Python dependencies include no ML libraries.

**Verdict:** proceed first with data instrumentation, migration/deployment verification, and a bounded shadow-mode analytics pilot. Start with demand forecasting and explainable reorder recommendations for a single store, then evaluate supplier lead times and anomaly alerts. Do not enable tenant-shared learning, automatic pricing, automatic PO submission, or production decisions until ownership boundaries, labels, historical coverage, temporal evaluation, permissions, auditability, and fail-open behavior are established.

Tenant/branch/warehouse ownership is not present in the inspected definitions. Many core entities use UUID primary keys and foreign keys, but several event references are intentionally polymorphic UUID pairs without an FK. Product and supplier entities are mutable and generally not versioned.

Not adequate as a model registry or recommendation audit by themselves. |

**Time semantics:** most event columns are `TIMESTAMPTZ`; some business dates (`order_date`, `received_date`, `payment_date`, attendance date, expenses) are `DATE`. `server/db/postgres.js` sets the PostgreSQL session timezone from `STORE_TIMEZONE`, and Compose defaults to `Asia/Dubai`; the forecast uses local JS date operations. This is a defined store-timezone intent, but live values and all code paths are not verified. Preserve UTC instants plus an explicit store/business timezone and derive business-day/hour features consistently. Separate event time from ingestion/update time for late edits and offline sync.

**Historical-state risks:** current product stock/price, supplier lead-time profile, customer balance, PO balance, and invoice status can change; current values cannot be used as though they were known at prediction time. `cost_price_at_time` is a useful sales snapshot, while price changes outside transactions and promotions are not reconstructible. Cascading deletes and nullable references may remove historical joins. `stock_movements` can help rebuild stock, but only with opening stock and complete, ordered events; this has not been tested against an applied database. No full scans or live queries were made.

## 5. Detailed Model-by-Model Findings

1. **Stockout prediction.** Predict remaining days/date per variant-location using confirmed sold quantity, timestamp, on-hand, purchase/return/adjustment movements and PO incoming quantities. Candidate inputs exist in `invoice_items`, `invoices`, `stock_movements`, `product_variants`, and PO tables. The label requires the date inventory reached zero, including observed unavailable periods; zero sales during a stockout must not be treated as zero demand. There is no branch/warehouse key, movement coverage is unverified, returns must be netted, and historical availability is not established. Start with intermittent-demand/time-series baselines; compare gradient boosting only after an availability-aware dataset exists. Measure time-to-stockout error, stockout recall, and service-level impact using rolling-origin evaluation. Leakage risk: current/future stock and PO status in historical features. **Changes:** immutable stock snapshot/event completeness, locations, and recommendation history. **Status: PARTIALLY READY.** Evidence: migrations `002_products.sql`, `003_stock.sql`, `006_invoices.sql`, `015_analytics.sql`; `forecastService.js`.

2. **Supplier reliability ranking.** Explainable score can combine on-time completion, delay, fill-rate, partials, cancellations, returns/defects, recency and confidence. Inputs in `purchase_orders`, PO lines, `stock_movements`, supplier returns and suppliers support a coarse historical score. Expected date vs full receipt date is only PO-level; cancelled remaining quantity and responsibility are not recorded. Buyer payment delays or internal holds cannot be attributed from schema alone. Add delivery/cancellation reason, responsible party, verified status and per-receipt event. Minimum sample sizes should be learned with confidence intervals/learning curves, not fixed arbitrary thresholds. Validate calibration and rank stability; show sample count and uncertainty. Leakage: current supplier profile and edited expected dates. **Status: PARTIALLY READY.** Evidence: `004_suppliers.sql`, `035_po_confirmed_at.sql`, `purchaseOrderService.js`, `analyticsService.js`.

3. **Supplier delivery-time prediction.** Predict time to first receipt and time to full receipt separately, conditioned on supplier/product/quantity/season. PO confirmed/order and expected dates plus stock movement timestamps provide partial signal; cumulative `quantity_received` overwrites the event history in the PO line. Movement rows can potentially reconstruct individual receipt quantities and times by PO+variant but not reliably map duplicate same-variant lines or represent cancelled remaining quantity. Use survival/time-to-event methods for incomplete/cancelled orders, or regression only on completed cohorts. Validate MAE/median absolute error and prediction-interval coverage with temporal supplier holdouts. Leakage: using final receipt status/date as feature. Add receipt event/line ID and cancellation/close reason. **Status: PARTIALLY READY.**

4. **Demand forecast and reorder optimization.** The current system aggregates confirmed invoice quantities into `sales_history_monthly`; monthly history loses daily/hourly peaks and zeros do not distinguish no demand from unavailable. Current `stock_qty`, pending PO, default lead time and costs exist, but MOQ, pack multiple, service target, carrying/storage costs, expiry, and supplier-specific item lead time need collection. Baseline seasonal-naive/intermittent-demand methods should precede XGBoost; optimize order quantity separately under lead-time demand, MOQ/pack, budget and shelf-life constraints. Use rolling time splits, WAPE/MASE and quantile/service-level backtests. Never validate by random row split. Leakage: contemporaneous stock, eventual PO receipt, current price/cost. **Status: PARTIALLY READY.** Current rule uses monthly averages, fixed seven-day buffer, and a 2x calendar-month peak multiplier (`server/services/forecastService.js`); this is not ML and its stored `confidence` is a history heuristic, not statistical uncertainty.

5. **Intelligent pricing.** Target quantity/contribution margin response to a *recommended* price, using transaction unit price, line discounts, returns, time, cost-at-time and inventory availability. Actual prices and cost snapshots are strong event facts, but offered prices during zero-sale periods, price-change effective history, promotions, reason codes, tax/fees and exposure are missing. Observational correlations cannot isolate price elasticity from promotions, seasonality or stock availability; safe causal experiments require explicit governance. Start with constrained descriptive elasticity/causal design and margin simulation, not automatic optimization. Validate profit and conversion impact with a controlled, approved experiment plus guardrails. Leakage: realized price/discount/stock after the decision time. Add price/promotion exposure events and recommendation/outcome history. **Status: PARTIALLY READY.** Output must be advisory; never write price changes automatically.

6. **Predictive stockout prevention.** Combine demand quantiles, current verified inventory, outstanding and dated receipt quantities, supplier delivery distributions, safety stock, and alert/recommendation state. Existing current stock, PO states, reorder recommendations and stock alerts provide a basic rules engine. No dependable supplier ETA model, location scope, stale recommendation handling across partial receives, or durable background worker/event queue is present. Begin daily reconciliation plus transactional idempotent alert creation; later add events. Alert precision/lead time and missed-stockout rate are the measures. A draft PO must be human-approved and must never auto-submit. **Status: PARTIALLY READY.**

7. **Store traffic forecasting.** Current completed invoices provide transaction counts/time, which predict transaction volume rather than people entering the store. Store hours, branch and campaign facts are not modeled sufficiently. Collect privacy-preserving aggregate visitor counts from a counter if actual footfall is required; otherwise name the capability “transaction volume forecast.” Use seasonal time-series baselines; validate hourly/daily count MAE and interval calibration. No identifiable visitor tracking is needed. **Status: DATA COLLECTION REQUIRED.**

8. **Product demand during peak hours.** Invoice timestamps joined to line quantity permit historical hourly sales for completed purchases. Required targets are per-variant hourly quantity, with periods of unavailability, branch/store timezone and holidays/campaigns. Current monthly rollup is too coarse; source invoices retain timestamps but no availability history/branch. Use hierarchical seasonal baselines or gradient boosting with time features only after reconstructing at-risk availability; evaluate rolling-origin WAPE/MASE and peak-period bias. **Status: PARTIALLY READY.**

9. **Peak inventory readiness.** Need the peak-hour quantile forecast, inventory by location, stock on the way by expected receipt, supplier lead-time uncertainty, safety policy and expiry. Existing sales/stock/PO tables and reorder UI support a prototype warning, but not shelf-life or branch-level readiness. Start as a daily advisory dashboard with explainable “expected demand before next receipt”; monitor missed and false warnings. Do not create or confirm POs autonomously. **Status: PARTIALLY READY.**

10. **Fraud / anomaly detection.** Events include refunds/returns, discounts, adjustments, cash drawer sessions/transactions, PO changes, users and activity logs. Define separate anomaly targets and features per action; validate who/when attribution and approval trail. Verified fraud labels are not present, so use deterministic controls and unsupervised/statistical triage (robust peer baselines, Isolation Forest only as one candidate), with human investigation outcomes. Evaluate alert precision, investigation yield, and subgroup false-positive rates; do not label a person fraudulent based on a score. Prevent leakage from investigation outcome, changed invoice state, or post-event notes. **Status: PARTIALLY READY.**

11. **Market basket analysis.** `invoice_items` supports product-pair/co-occurrence mining within confirmed invoices. Exclude cancelled invoices; net returns/replacements, define minimum basket quality and anonymous sales behavior. FP-Growth or simple support/confidence/lift is appropriate; compare stability by season and minimum support, avoid rare-item privacy leakage. Evaluate lift and actionability in a human-reviewed pilot, not only accuracy. The line-item snapshots can preserve item identity if catalog entries later change. **Status: PARTIALLY READY.**

12. **Expiry and waste prediction.** No batch/lot stock ledger, expiry date, receipt lot allocation or explicit waste/damage event is defined in reviewed schema. Product-level `stock_qty`, FIFO cost valuation and generic adjustment reason cannot identify which units will expire; accounting FIFO is not FEFO rotation. Add lot/receipt-to-lot quantity movements, expiry, disposition and waste reason before forecasting. Then estimate sell-through per lot and probability of expiry before sale; evaluate waste value/units and false warnings. **Status: SCHEMA CHANGES REQUIRED.**

13. **Customer churn.** Customer-linked invoice times and profile creation allow recency/frequency summaries; customer payments are a separate financial event. Unknown repeat rate, anonymous proportion, duplicate customer identities and sufficient history prevent a data sufficiency claim. Define churn relative to customer purchase cadence and business horizon, handle right-censoring/new customers and returns; use survival or simple recency baselines before classifier. Validate time-split recall/precision and calibration by customer cohort. Avoid PII features and cross-customer leakage. **Status: PARTIALLY READY; live sample sufficiency NOT VERIFIED.**

14. **Staff demand forecasting.** Attendance/check-in plus cashier actor on sales can approximate staff presence and transaction volume but not labor demand, queue pressure, service durations or schedules. Collect planned shift and station/role data and privacy-preserving hourly arrivals/queue/service outcomes; never infer productivity or performance from sales alone. Forecast workload by hour and compare schedule scenarios; validate queue/wait or labor coverage outcomes. **Status: DATA COLLECTION REQUIRED.**

15. **Dead stock.** Product-level last-sale, sales quantities, current stock, costs and PO history can support an explainable slow-mover score. Must account for stockout-censored sales, seasonality, new product cold start, returns, substitutes and stock age. Use rules/quantile demand and classify “at risk” horizons with time-based validation; measure useful identification and false write-down prompts. Lot age is absent, so product-wide stock age cannot be known. **Status: PARTIALLY READY.**

16. **Cash flow and purchase budget.** Revenue, invoice payment methods, customer collections, supplier payments, bills, expenses, cash/bank transactions and journal entries exist. Reconstruct future actual receipts/disbursements by due date, payment behavior and committed incoming/outgoing POs; sales revenue is not cash and mutable customer/PO balances are not historical point-in-time truth. Validate against reconciled cash/bank actuals using rolling forecasts and cash shortfall recall. Confirm journal posting/reversal completeness and currency before training. **Status: PARTIALLY READY; reconciliation/data quality NOT VERIFIED.**

17. **Brand quality and return intelligence.** Product brand is free text, returns include item, reason, condition and sometimes supplier/PO references, and sales counts can form rates. No brand normalization, purchase batch or supplier receipt lot links connect a defect to a source batch; reasons may mean preference, wrong item or defect. Add controlled reason taxonomy, verified root cause, lot/supplier attribution and resolution. Use rates with exposure denominators and Bayesian shrinkage/confidence; validate against independently reviewed defects. Warn only; do not block a PO or assert quality from sparse return text. **Status: SCHEMA CHANGES REQUIRED.**

## 6. Data Collection Gaps and Historical Data Quality

No explicitly authorized read-only database connection was identified or used. No database statistics are available from this audit. The following are therefore **NOT VERIFIED**: earliest/latest relevant dates; counts of sales, variants, suppliers, POs, partial receipts, returns, customers, price changes; seasonal coverage; missing/duplicate/orphan rates; invalid timestamps; class imbalance; retention; and whether each listed migration has been applied.

Before model selection, create a bounded aggregate-only data-quality inventory on a separately approved read-only connection. Check monthly coverage by entity and event type, null rates, duplicate business keys, invoice state transitions, stock movement continuity (`qty_before` vs previous `qty_after`), negative/over-received PO quantities, PO-to-movement match rates, return link completeness, out-of-order/backdated events, and price/cost availability. Do not export row-level customer, employee, payment or sales records. Use time-based train/validation/test windows and rolling-origin evaluation; plot learning curves and confidence intervals to decide if each target has enough effective history. No minimum sample counts are fabricated here.

Per-model data sufficiency is **NOT VERIFIED** for every model. Even if schema fields exist, only an aggregate readiness query and label audit can establish historical span, density, coverage, and bias. The monthly sales aggregate cannot substantiate daily/hourly/peak forecasts without re-aggregating source invoices and proving availability.

Historical backfill from movement references is conditional and may be ambiguous. |
| Inventory lot / expiry / waste | Lot/receipt provenance, lot quantities and movements, expiry date, disposition/waste quantity/reason, and location. Enforce nonnegative balances through transactional service rules; indexes on variant/location/expiry. Historical backfill generally impossible without source lot records. Needed for expiry and batch quality. |
| Price/promotion exposure | Append-only price effective intervals or change events with variant/location, old/new price, reason, actor/time; promotion/campaign window and eligible items; transaction-level applied promotion/override metadata. Add constraints to prevent overlapping active intervals per scope. Backfill from invoice snapshots only gives realized prices, not offered-price/no-sale exposures. |
| Model registry and evaluation | Model/version identity, code/data feature version, training window, approval status, artifact reference/hash, metrics by segment, created/retired times; immutable evaluation records. Keep artifact storage outside row payloads and restrict access. No model artifacts should be stored in source repository. |
| Prediction/recommendation lifecycle | Prediction ID, model/version, target entity + location, as-of feature time, horizon, output, interval/confidence, generated/expiry times, status, explanation/feature snapshot reference, actor approval, and eventual outcome. Idempotency key and unique key per target/horizon/run to avoid duplicates. Restrict PII; retain history rather than overwrite the current recommendation. |
| Operational reason/outcome taxonomy | Controlled supplier delay/cancellation responsibility and verified reason; return defect root cause, severity and adjudication; anomaly investigation disposition; recommendation accepted/rejected/edited and reason. Audit who verified and when. Do not backfill free text as verified labels automatically. |
| Demand and quality aggregates | Optional precomputed daily/hourly variant-location demand and availability features with source watermark/version, plus quality-rate aggregates with denominator. Prefer source facts as system of record; document deterministic rebuild and avoid duplicating canonical sales/stock data. |

Migration risks include lock time/backfill size, old app compatibility, indexes, nullable-to-required transitions, and mixed application versions. Use expand/backfill/validate/contract sequencing, bounded backfills outside cashier latency, and restore rehearsal. Existing database rollback/backup procedures should be assessed before release. No migration was written or run.

## 8. Backend Change Proposal

Keep POS transaction paths independent of model availability. Recommended eventual boundary is an internal, authenticated prediction/recommendation API and asynchronous worker. Backend should assemble tenant/location-scoped point-in-time features, validate permissions and freshness, persist predictions and user decisions, apply idempotent advisory notifications, and expose only bounded DTOs. Do not have an ML service issue sales, stock, payment, pricing or PO mutations. Future endpoints should be read-only to consume recommendations and separate permission-gated actions to acknowledge/approve drafts. Add rate limits, strict timeouts, request IDs, audit events, schema/version compatibility, and fail-open behavior for ordinary POS flows.

Any model response must include model version, feature as-of time, horizon, units, uncertainty, expiry/freshness, and explanation. A stale, missing, or malformed response should suppress the advisory and leave cashier workflows intact. Draft PO creation should be explicit, deduplicated, reviewable and never submitted automatically. New use of customer/staff information requires data minimization and a retention/access policy.

## 9. Frontend Change Proposal

Extend the existing analytics surface only after permission and data contracts exist. Show recommendation reason, inputs, date/horizon, uncertainty/sample coverage, model version, generated time, stale state, and accept/dismiss/edit actions with outcome capture. Distinguish a transaction-volume forecast from foot traffic. Supplier scores must expose component rates, sample size, confidence, and exclusions. Pricing is recommendation-only and must show margin guardrails; quality warnings are advisory. Dashboards should be branch-filtered only after branch-scoped data and authorization are implemented. Provide an unobtrusive unavailable state so an AI outage never blocks POS work. Frontend changes are proposals only; no UI was changed.

## 10. Infrastructure Assessment

| Capability | Current evidence / requirement |
|---|---|
| Separate Python service | Compose already offers an optional FastAPI sidecar under `ml` profile and a Dockerfile. This is a useful boundary, but current routes are read-only parity/analytics, not inference. Compose exposes a host port and does not document resource quotas. |
| Background jobs | Current in-process Node timers prove scheduling pattern exists, but not durable delivery, retry, deduplication, leader election, monitoring, or recovery. Do not put training or long scoring work on cashier request threads. A separate worker/job runner is needed for robust periodic tasks. |
| Storage/versioning | No model artifact volume/bucket, registry, lineage or rollback protocol is configured. Add controlled, versioned artifact storage with checksums and rollback metadata; keep training data protected and minimize retention. |
| Queue/event-driven inference | No broker/queue is configured. Prefer scheduled batch inference and reconciliation initially; evaluate durable queue only when event latency warrants operational cost. Socket.IO is delivery, not durable work queue. |
| Monitoring and recovery | Health checks exist for app/service/DB, but no model metrics, drift/data-quality alerts, prediction failure SLO or circuit breaker is shown. POS should not depend on ML health. |
| Capacity | Host CPU/RAM, disk, number of stores/registers, transaction concurrency and DB connection limit are unknown. Compose sets API PG pool max 10 by default in code, but the aggregate number of app processes/services and actual DB `max_connections` are NOT VERIFIED. | Backup/restore | Existing backup scheduler/services are present, but model artifacts, feature definitions and evaluation records are not yet part of a documented restore/rollback plan. Test backup restoration with sidecar unavailable. |

**Recommendation:** hybrid. Keep online business rules and feature permissions in Express; run scheduled, batch inference in the optional isolated FastAPI/worker environment; persist advisory output in PostgreSQL; use explicit API contracts and no synchronous model dependency in checkout. Start with one process/one store, no GPU, no queue until proven necessary. Move to a durable worker/queue only when measurements require it. The POS must continue normally if the Python service is stopped.

## 11. Security & Tenant Isolation

Current reviewed schema lacks tenant/branch keys, so row-level isolation cannot be asserted for ML. Do not implement cross-tenant training or cache keys based only on product/supplier IDs. Before multi-tenant inference, every source query, feature cache, prediction key, artifact lineage and API authorization must include tenant and location; test adversarial cross-tenant access. Prefer tenant-local training initially. A future shared model may use only explicitly authorized, minimized, de-identified aggregate features after legal/product approval and leakage review; per-tenant calibration can remain separate.

Use a separate least-privilege database identity for inference, initially SELECT-only on approved views or feature extracts; do not pass the POS write credential into a model container. FastAPI currently receives PostgreSQL credentials through the shared `.env` Compose pattern and `get_engine()`; a future least-privilege secret and network policy are required. Do not expose the ML port to the LAN without authentication and TLS policy; the current Compose `ports` mapping makes network exposure a deployment concern. Continue JWT and permission checks, with explicit ML view/manage/approve permissions. Minimize PII, exclude names/phones/addresses/employee identifiers from features by default, audit sensitive model access, encrypt transport/backups, define retention, and protect model artifacts/exports. Check cache keys, logs, error traces and explanation fields for sensitive data.

## 12. Recommended Implementation Roadmap

1. **Establish facts and ownership.** Verify deployment topology, database version, applied migration ledger, store/branch meaning, retention and backup/restore using authorized read-only/admin procedures. Decide whether the product is single-store or multi-tenant before adding AI data structures.
2. **Run aggregate data-quality profiling.** On an explicitly approved read-only connection, execute bounded aggregate checks only. Reconcile invoice confirmation/cancellation/return semantics; quantify history windows and sparsity; verify stock event continuity and PO/receipt linkage. Publish quality criteria and owner sign-off.
3. **Instrument events before modeling.** Add location ownership, receipt events, time-aware price/promotion exposure, reason taxonomies, and (only where needed) lot/expiry or shifts. Stage schemas backward-compatibly; no inferred backfill presented as ground truth.
4. **Build a reproducible dataset and baselines.** Use privacy-minimized point-in-time feature logic, data version/watermark, temporal splits, leakage tests, simple seasonal/intermittent baselines, and rolling backtests. Establish learning curves and segment checks.
5. **Pilot demand and reorder in shadow mode.** Use one site and selected variants; compare current rule with forecasts, record uncertainty and outcomes, expose advisory only, and monitor stockout/overstock impact without automated ordering.
6. **Add explainable supplier lead-time/reliability and operational anomaly triage.** Only after receipt/reason labels are complete. Human review and disposition capture are required; anomalies never imply guilt.
7. **Evaluate remaining domains independently.** Basket analysis can follow once returns/cancellations are netted; cashflow after finance reconciliation; churn after repeat/anonymous customer analysis; pricing only after promotion/availability instrumentation and approved experimentation; expiry, brand quality and staffing only after their missing domain events are collected.
8. **Productionize gradually.** Isolated batch worker, least-privilege identity, durable versioned artifacts, monitoring, rollback, restore tests, fail-open POS, permissions, retention, and staged rollout. Gate each model on business-owner validation and measurable offline/online criteria.

## 13. Risk Register

| Risk | Impact | Mitigation / gate |
|---|---|---|
| Treating migration files as live schema or assuming sufficient history | Models fail or silently train on incomplete data | Verify applied migration ledger and profile with safe aggregate queries before design freeze. |
| Stockouts misread as low demand | Systematic under-ordering | Reconstruct availability from complete movements and opening balances; collect location snapshots; mask unavailable exposure. |
| Partial PO receipt treated as full delivery | Bad lead-time/ranking labels | Add receipt events, first/full delivery targets, cancelled quantity and verified reason; model censored orders. |
| No branch/tenant dimension | Cross-store leakage, wrong inventory advice, unauthorized disclosure | Resolve ownership model before multi-store AI; enforce scope in DB, API, feature, artifact and cache layers. |
| Current mutable values leak future state | Inflated backtests and poor live results | Point-in-time joins, immutable effective events, temporal split and leakage tests. |
| Monthly aggregates used for hourly tasks | Missed peaks and false confidence | Use transaction facts with availability and store timezone; retain hourly/daily feature lineage. |
| Sparse / biased labels | Unstable supplier, churn, fraud or defect predictions | Confidence/sample reporting, learning curves, human labels, threshold governance and abstention. |
| Unreviewed score interpreted as fraud or poor supplier quality | Employee/supplier harm | Advisory language, explainability, human review, appeal/correction path; no automatic blocking. |
| ML outage or latency affects cashier operations | Sales disruption | Async/batch inference, strict timeouts, cache freshness, circuit breaker; checkout never calls a mandatory model. |
| Duplicate scheduled runs or stale recommendations | Conflicting orders/alerts | Durable job lock/idempotency, unique recommendation key, watermark, expiry and reconciliation. |
| Shared DB credential / network exposure | Unauthorized writes or data exfiltration | Least-privilege read-only identity, internal networking, authenticated TLS endpoints, secret separation. |
| PII or employee data used unnecessarily | Privacy/security harm | Feature minimization, aggregation, retention limits, access controls, documented purpose and review. |
| Artifacts/data pipeline not backed up or reversible | Lost model state or irreproducible predictions | Version/hash, data watermark, restore/rollback rehearsal and artifact lifecycle policy. |

## 15. Final Verdict

**The application can support a carefully scoped advisory AI/analytics program after foundational data work, but the inspected evidence does not support immediate deployment of a comprehensive trained ML platform.** The strongest starting point is an offline/shadow demand forecast over confirmed invoice lines plus verified inventory availability, followed by human-reviewed reorder recommendations. Existing transaction snapshots, stock movement ledger, PO and finance domains, authorization, Docker boundary and forecast UI are meaningful assets.

The blockers are concrete: no verified live data profile; no confirmed migration state; monthly demand aggregation and unknown availability censoring; no branch/tenant/warehouse ownership in reviewed schema; incomplete per-receipt history and reason labels; no lot/expiry events; no price/promotion exposure history; no staff schedule or actual traffic measurement; no ML lifecycle/monitoring; and no demonstrated least-privilege ML database/network boundary. Historical sample sufficiency for every capability remains **NOT VERIFIED**.

### Decision questions before implementation

1. Is each deployment one store/company, or must one database support multiple tenants, branches and warehouses?
2. Is there an existing explicitly approved read-only database connection and what is its allowed scope? (No such connection was used or verified in this audit.)
3. Which initial business objective and owner should be piloted: reducing stockouts, reducing overstock, supplier performance, or another outcome?
4. Can operators reliably record each partial receipt, supplier/buyer delay cause, return defect cause, price/promotion exposure, and inventory lot/expiry where relevant?
5. What hardware envelope, POS availability target, and model-service network policy must be supported?
6. What data retention, privacy, employee monitoring, tenant-sharing and human-approval policies apply to recommendations?
